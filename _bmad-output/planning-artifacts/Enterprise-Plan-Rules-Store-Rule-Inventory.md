# Enterprise Plan Rules Store — Rule Inventory and CRTC Traceability

**Analysis date:** 10 November 2026  
**Scope:** Code, schema, API, user interface, seed data, configuration and tests under [enterprise-plan-rules-store](../../prototype/enterprise-plan-rules-store/).  
**Regulatory source:** [Telecom Regulatory Policy CRTC 2026-78, “Enhancing self-service mechanisms”](../../source/telecom%20regulatory%20policy%20CRTC%202026-78.pdf), issued 24 April 2026.  
**Nature of this document:** Static analysis of an illustrative administrative prototype, not a compliance determination or legal advice.

## 1. Executive summary

The prototype manages wireless and Internet plan records and **directional plan-to-plan eligibility decisions**. Each configured rule contains an allow/deny flag, two free-text messages, a status, a version and effective dates. The eligibility endpoint retrieves an effective active rule for an exact ordered pair; it does not calculate eligibility from customer, contract, pricing or account information.

The policy's paragraphs 13 and 16 establish that self-service must allow customers to modify plans, including upgrading and downgrading. Paragraphs 14–15 address transparency, informed and express consent, resulting contract changes, and whether prior contract terms can be restored. The prototype's decision and warning fields are **potential supporting inputs** to those outcomes, but the policy does not mandate this rules store, its data model, its particular decisions, or a specific discount-warning/EDUF field. The store is not itself a customer-facing self-service mechanism and does not establish compliance.

Most rules below are **prototype design or validation rules**, not rules found in CRTC 2026-78. The three seeded decisions are synthetic examples, not regulatory determinations. In particular, the seeded wireless downgrade denial and the default “no active rule” ineligibility must not be interpreted as permitted grounds to deny a customer's change; any real restrictions and their effect on access to self-service require regulatory/legal review.

### Classification used throughout

| Label | Meaning |
|---|---|
| **Related — paras. 13, 16** | Supports a plan-modification decision relevant to self-service; exact restriction or technical implementation is not mandated by the cited paragraphs. |
| **Related — paras. 14–15** | Could carry information useful for transparency and informed decisions; the field alone does not meet the disclosure or consent obligation. |
| **No direct reference** | No matching requirement for the specific rule was identified in the supplied policy. Other law, Codes or contracts were not independently assessed. |

## 3. Decision and eligibility rules

| ID | Implemented rule / observable result | Code evidence | CRTC 2026-78 reference |
|---|---|---|---|
| D01 | A rule applies to one **ordered** `fromPlan` → `toPlan` pair. An A → B decision does not imply B → A. | [repository.js](../../prototype/enterprise-plan-rules-store/server/src/repository.js#L17), [App.jsx](../../prototype/enterprise-plan-rules-store/client/src/App.jsx#L301) | **Related — paras. 13, 16:** plan modification, including upgrades/downgrades. Exact directional matching is a design choice, not a prescribed regulatory test. |
| D02 | For a matching effective active rule, `eligible` equals its configured Boolean `allowed`; either an allowed or denied decision can be stored. No customer-specific or account-specific criteria are evaluated. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L236), [plan-rule.js](../../prototype/enterprise-plan-rules-store/server/src/models/plan-rule.js#L5) | **Related — paras. 13, 16** only at the general plan-change level. The policy does not approve any particular denial. |
| D03 | An active record is effective only when `effectiveFrom <= now` and `effectiveTo` is null or `effectiveTo > now`. The start is inclusive; the end is exclusive. A draft, retired, future or expired record does not qualify. | [repository.js](../../prototype/enterprise-plan-rules-store/server/src/repository.js#L17) | **No direct reference.** Policy para. 13 concerns when customer actions take effect, not the effective interval of an administrative rule. |
| D04 | When no effective active record matches, `GET /api/eligibility/:fromPlanId/:toPlanId` returns HTTP 200 with `eligible: false`, `reason: NO_ACTIVE_RULE` and an explanation. This is a missing-configuration outcome, not proof that the underlying plan change is legally prohibited. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L236) | **Related — paras. 13, 16**, because a downstream consumer might block modification. The policy does not prescribe “missing rule means ineligible”; evaluate any resulting barrier. |
| D05 | The detailed relationship lookup `GET /api/plan-rules/:fromPlanId/:toPlanId` returns HTTP 404 / `RULE_NOT_FOUND` when no effective active exact pair exists; an effective rule, including an explicit denied rule, returns the full record, populated plans and `eligible = allowed`. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L215) | **Related — paras. 13, 16** only in the general sense that a result may support a plan-change journey. The HTTP response is a prototype design decision. |
| D06 | Both lookup APIs require syntactically valid MongoDB object identifiers. They query the pair directly and do not separately check whether each valid ID identifies an existing plan before returning a no-rule outcome. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L215) | **No direct reference.** |
| D07 | When a rule is found, the eligibility response includes decision, rule ID, version, status, effective dates, both populated plans, `EDUFMessage` and `discountLossWarning`. It does not execute the change. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L251) | **Related — paras. 14–15:** information might support transparency, but returning data to an API consumer does not itself disclose it to the customer or obtain consent. |
| D08 | The rule only compares plan identifiers. Plan price, data allowance, term, features and service type are not used to compute allowed/denied; there is no automated assessment of whether a change is an upgrade/downgrade. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L236), [repository.js](../../prototype/enterprise-plan-rules-store/server/src/repository.js#L17) | **Related — paras. 13, 16** as general context, not a prescribed eligibility algorithm. |
| D09 | The API does not enforce that the two plans share a service type or provider. Any two distinct existing plan IDs can form a rule, including a wireless-to-Internet pair. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L60), [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L102) | **No direct reference.** No inference that such a relationship represents an approved product change. |

## 6. Revision, activation and deletion rules

| ID | Implemented rule / observable result | Code evidence | CRTC 2026-78 reference |
|---|---|---|---|
| L01 | On create, version is one more than the highest **currently stored** version for the ordered pair. A unique database index enforces `(fromPlan, toPlan, version)` uniqueness. A concurrent duplicate version receives HTTP 409 / `RULE_VERSION_CONFLICT`. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L196), [plan-rule.js](../../prototype/enterprise-plan-rules-store/server/src/models/plan-rule.js#L31), [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L109) | **No direct reference.** Version numbers are not a guaranteed permanent sequence: a deleted highest revision can allow that number to be reused. |
| L02 | At most one `ACTIVE` revision per ordered pair is enforced by a MongoDB partial unique index on status, independent of effective date. Drafts and retired records are not subject to that active-pair index. | [plan-rule.js](../../prototype/enterprise-plan-rules-store/server/src/models/plan-rule.js#L23), [index.js](../../prototype/enterprise-plan-rules-store/server/src/index.js#L15) | **No direct reference.** |
| L03 | Creating a rule through the UI submits no status and therefore creates a draft. The API also accepts explicit `ACTIVE` or `RETIRED` status on creation; an `ACTIVE` rule with an end at or before the current clock is rejected. | [App.jsx](../../prototype/enterprise-plan-rules-store/client/src/App.jsx#L119), [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L196) | **No direct reference.** |
| L04 | API creation can set a rule to `ACTIVE` even if `effectiveFrom` is in the future. It occupies the active-pair slot but is not returned by the effective-rule lookup until its start. By contrast, the explicit activation endpoint rejects early activation. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L196), [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L304), [repository.js](../../prototype/enterprise-plan-rules-store/server/src/repository.js#L17) | **No direct reference.** This distinction can cause no effective decision while the future active record occupies the slot. |
| L05 | Direct creation of a second `ACTIVE` record for the same pair conflicts with the unique index and returns `DUPLICATE_ACTIVE_PAIR`; creation occurs before the subsequent attempt to retire other active records. Use the draft activation flow for replacement rather than assuming direct active creation replaces an existing one. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L196), [plan-rule.js](../../prototype/enterprise-plan-rules-store/server/src/models/plan-rule.js#L23) | **No direct reference.** |
| L06 | Updating a rule via `PUT /api/plan-rules/:id` creates a **new draft** with the next currently available version; it does not overwrite the old rule. The from/to direction must remain unchanged, and both plans must still exist. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L280) | **No direct reference.** |
| L07 | Activation rejects a retired rule, a rule whose start is in the future, or a rule whose end is at/before the current time. For an eligible activation, other active revisions of the same direction are marked retired with their end set to the activation clock, then the selected record becomes active. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L304), [repository.js](../../prototype/enterprise-plan-rules-store/server/src/repository.js#L27) | **No direct reference.** The sequential operations are not enclosed in a database transaction in this code; do not assume atomic replacement. |
| L08 | Activation sets the selected revision's `effectiveTo` to **null**, even if a future end date was configured. The endpoint does not require the selected record to be a draft: an already active record can be activated again if it passes date checks. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L309) | **No direct reference.** The effective end set through the draft form does not survive activation; do not assume scheduled expiry is retained. |
| L09 | Deleting an active revision instead marks it `RETIRED`, sets its end to the current clock and retains it. Deleting a draft **or retired** revision actually removes it. History is therefore not guaranteed permanent. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L327) | **No direct reference.** The policy does not prescribe this rule-revision retention model. |
| L10 | Database duplicate-key errors map to conflict responses; invalid model/cast input maps to HTTP 400, invalid JSON to 400, request bodies above 100 KB to 413, and unexpected errors to 500. These are technical/API handling rules. | [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L109), [app.js](../../prototype/enterprise-plan-rules-store/server/src/app.js#L129) | **No direct reference.** |

## 8. Rules defined in the seed script

The seed creates or reuses four sample plans by provider/name. It creates a sample rule only if **no revision of any status** already exists for that ordered pair. Consequently a seeded sample may be skipped and an existing database may not contain the exact values below. All examples are illustrative, `ACTIVE`, version 1, start at `2026-01-01T00:00:00.000Z`, and omit an end date. See [seed.js](../../prototype/enterprise-plan-rules-store/server/src/seed.js#L14) and [seed.js](../../prototype/enterprise-plan-rules-store/server/src/seed.js#L60).

| ID | From → to | Allowed | Exact EDUF message | Exact discount warning | Policy reference / interpretation |
|---|---|---:|---|---|---|
| S01 | Northstar Wireless (Illustrative), Everyday 20 GB ($55/month) → Plus 60 GB ($75/month) | `true` | “Illustrative: Your plan change is available.” | “No discount-loss warning for this example.” | **Related — paras. 13, 16:** example upgrade; neither the specific plan nor decision is prescribed. |
| S02 | Northstar Wireless (Illustrative), Plus 60 GB ($75/month) → Everyday 20 GB ($55/month) | `false` | “Illustrative: This plan change is not available.” | “A promotional discount may end if you change plans.” | **Related — paras. 13, 16:** this example denies a downgrade; the policy requires a self-service mechanism enabling downgrades and does not authorize this specific denial. **Para. 15** is context for disclosure if contract terms actually change. Legal review is required before any real restriction is applied. |
| S03 | Northstar Internet (Illustrative), Home Internet 100 ($60/month) → Home Internet 500 ($85/month) | `true` | “Illustrative: Your plan change is available.” | “No discount-loss warning for this example.” | **Related — paras. 13, 16:** example upgrade; the specific decision is not prescribed. |

There is **no seeded** Home Internet 500 → Home Internet 100 rule. In a clean seed-only database that reverse lookup has no effective rule and the eligibility API returns `eligible: false` / `NO_ACTIVE_RULE`; it is not an explicit denied rule and must not be represented as a lawful downgrade prohibition. Other plan pairs likewise have no seeded rule unless listed above. The seed code does not establish the current database state.

## 9. CRTC requirements versus prototype coverage

This table lists related policy requirements that are relevant to interpreting the implementation; it is **not** a claim that the prototype satisfies them.

| Policy source | Requirement or guidance | What the prototype does / does not do |
|---|---|---|
| Paras. 13, 16, 42–43 | An easy-to-use mechanism must enable customers to modify, including upgrade/downgrade and add/remove services, or cancel without a live representative, subject to the stated clarification exception. | Returns plan-to-plan eligibility for two service types. It has no customer self-service journey, service add/remove or cancellation flow. A denial or missing-rule result must be evaluated for its impact on the actual journey. |
| Para. 13 | Actions take effect immediately to the greatest extent possible. | Does not execute customer actions or measure their actual effect. Effective dates in this store describe **rule availability**, not customer fulfilment. |
| Paras. 14–15 | The mechanism must be transparent and enable informed, express consent; for changes, customers are informed of resulting contract changes and whether they can return to prior terms. | Stores two arbitrary messages and plan details. It does not determine actual contract changes, assess restoration, display disclosures to a customer or capture consent. |
| Para. 17 and footnote 5 to para. 15 | Definition applies to individual and small-business customers; “customer” includes account holder or authorized user. | Does not model customer segment, identity, authorization or permissions; therefore it cannot establish coverage for these populations. |
| Paras. 28–29, 44 | Written confirmation for actions taken through self-service; expected confirmation timeframe stated within the mechanism. | No customer communications, delivery tracking or confirmation-timeframe disclosure is implemented. An API response is not a delivered customer confirmation. |
| Paras. 26–27, 44 | No fees to access any type of customer service. Para. 27 distinguishes action fees and references Telecom Regulatory Policy 2026-43. | No fee assessment, billing or access-fee control. `EDUFMessage` is just text and cannot establish that an action fee is permitted. |
| Paras. 30–31, 45 | Existing accessibility and privacy protections apply; accessible mechanisms are encouraged, as is avoiding exclusive reliance on live service for accommodations. | An admin selector has keyboard/ARIA features, but there is no demonstrated customer-facing accessibility, privacy or accommodation control. |
| Paras. 38–39, 43 | Applies to all service providers as stated; self-service implementation/enforcement is set for 26 April 2027. | No provider classification or compliance-date control. The synthetic rule start date is unrelated to the regulatory implementation date. |

## 10. Verification and follow-up

The existing [server tests](../../prototype/enterprise-plan-rules-store/server/test/app.test.js) exercise plan and rule CRUD, input rejection, active-pair conflict, directionality, missing/denied decisions, revisions, activation, retirement, and future/expired dates using an **in-memory repository**. They do not prove MongoDB index behaviour or end-to-end subscriber compliance. The [client tests](../../prototype/enterprise-plan-rules-store/client/src/App.test.jsx) mock the API and cover admin flows, lookup, selection and UI behaviour. The [API client test](../../prototype/enterprise-plan-rules-store/client/src/api.test.js) checks preservation of a missing-rule error. These tests were inspected, not executed for this document.

For an operational inventory, obtain an approved export of **all** plan and rule revisions, including expired and denied rules; record extract time, environment and versions; compare each pair and message with approved product/legal criteria; and identify missing eligible pairs separately from express denials. Before using these decisions in a real customer journey, validate applicability, account context, real restrictions and consequences, legal fee treatment, restoration disclosures, effective-time behaviour, consent, confirmation and downstream fulfilment. Assess the lifecycle observations in L04–L09 and refer to the [detailed ecommerce test plan](./CRTC-2026-78-Ecommerce-Detailed-Test-Plan.md) for broader customer-journey testing.
